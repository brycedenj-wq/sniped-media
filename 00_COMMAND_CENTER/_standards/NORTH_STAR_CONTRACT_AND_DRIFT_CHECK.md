# NORTH STAR CONTRACT + DRIFT CHECK (permanent operating rule)

**Installed:** 2026-06-26 · **Status:** permanent. Applies to every serious build. This rule exists because the recurring failure was producing nodes (gates, proofs, intakes, single renders, strategy-only docs) instead of the actual product, and confusing "copy exists" with "built."

## The capability assumption (in-house by default)

The OS is assumed capable of building, in-house, every piece of the commercial puzzle: creative direction, worldbuilding, storytelling, character and subject systems, graphic design, identity and logos and marks, branding, websites, landing pages, pitch decks, social content, cold outreach, marketing strategy, offer architecture, business model, scaling plan, CRM and Notion structure, n8n and automation handoff, proof dashboard, asset production plan, execution plan. Do NOT outsource by default. Never say "give this to a designer" or "paste this into a builder." Assume the site, the mark system (as SVG), the deck, the forms, the Notion schema, the automation map, the outreach system, and the visual assets get built internally. Human taste review still gates everything; capability is in-house unless explicitly blocked (spend, account access, or a real tool gap).

## RULE 1 · Before any serious build, write a NORTH STAR CONTRACT and make it internally consistent before executing. If it is missing or vague, STOP. Do not build.

The contract answers eight questions:

1. WHAT IS THE ACTUAL PRODUCT? Not the gate, not the render, not the proof branch, not the workflow. Name the real deliverable.
2. WHAT IS THE ACTIVE LANE? (internal engine, client universe package, THE HOUSE product, my personal universe, first proof sprint, automation handoff, etc.) Pick ONE. Do not blend lanes.
3. WHAT IS EXPLICITLY NOT THE TASK? Name the drift traps (W5, n8n, outreach, regression, corpus reread, first-client hunt, strategy-only doc, single render, single character, etc.).
4. WHAT DOES DONE MEAN? Define the finished artifact concretely. For a universe, done means the full commercial package, not one image.
5. WHAT CAN BE BUILT IN-HOUSE? Assume web, design, deck, CRM, Notion, automation maps, copy, offer, visual system, and content are internal unless explicitly blocked.
6. WHAT NEEDS OPERATOR TASTE APPROVAL? Name the subjective gates before execution.
7. WHAT HARD BOUNDARIES APPLY? No spend, send, post, public naming, contact, or render without explicit approval. No fake proof. No em-dashes.
8. WHAT IS THE SINGLE NEXT ACTION? One action only.

## RULE 2 · After every major output, run the DRIFT CHECK.

- Did we produce the actual product, or just a node?
- Did we confuse a gate with the product?
- Did we outsource something we can build in-house?
- Did we ask BJ for info already in the corpus?
- Did we expand into automation, outreach, W5, or proofing without approval?
- Did we preserve the active lane?
- Did we crown an unverified name?
- Did we use a generic agency name because it sounded clean?
- Did we check ownership before building around a name?
- Does the name feel actually new, custom, and on-brand right now?

If any answer is bad, name it and correct it before moving on.

## RULE 3 · NAME OWNERSHIP + FRESHNESS GATE (hard front gate, not late polish)

No name is used as a product name, folder title, deck title, site title, or offer title until it passes the gate at 00_COMMAND_CENTER/_standards/NAME_OWNERSHIP_AND_FRESHNESS_GATE.md. A name that only sounds clean in a document has NOT passed. Until a name passes, use a neutral internal codename only (for example THE_HOUSE) and build nothing public-facing around an unverified name. Do not crown a name from vibes. If availability is not actually checked, label the name UNVERIFIED, never available.

## How to use it
- Serious build = any production task (a universe, a product, a site, a campaign, a deck, a client deliverable, a capability buildout). Casual chat, quick notes, and low-risk lookups do not need a contract.
- The contract is a short doc written and consistency-checked before the first build action.
- The drift check runs at the end of every major output and is reported honestly.
