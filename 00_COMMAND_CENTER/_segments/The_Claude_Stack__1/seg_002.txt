teams When the work requires multiple specialists who must coordinate with each other (not just report back to a parent), agent teams are the correct architecture. How teams differ
from sub-agents Sub-agents report back to the parent only. Hub-and-spoke communication. The parent coordinates everything. Agent teams share a task list (a scratchpad or message
board) that all teammates can read and write. Teammate A can see Teammate B's output without the parent relaying it. Sub-agents start fresh with no context inheritance. Agent teams
also start fresh, but the shared scratchpad provides coordination across independent context windows. Sub-agents are cheaper. Agent teams cost more tokens. The tradeoff:
coordination quality versus token budget. When to use agent teams Content repurposing where a blog post, a carousel, and a newsletter all need to share voice and key frameworks.
The content writer, the designer, and the editor benefit from seeing each other's work. Full-stack application builds where frontend and backend must coordinate on API contracts. A
frontend agent and a backend agent need to agree on data shape. Multi-author book production. A chapter drafter, an editor, and a voice auditor pass work between each other until
the chapter ships. The technical reality Agent teams require Claude Code version 2.1.32+. Enabled in settings.json. An experimental flag as of the time of writing. Each teammate
gets its own context window. Context inheritance between teammates does not happen automatically. Coordination is through the shared task list. tmux or iTerm2 split view lets you
monitor multiple teammates simultaneously. Useful for debugging. Not required for production runs. 8.5 The complexity budget Every additional agent adds tokens and adds
coordination overhead. The decision to add an agent should be justified by a specific gain in output quality or speed. A rough scoring system to decide when to escalate: Task
complexity 2 out of 10: single agent. No delegation needed. Task complexity 6 out of 10: sub-agents. Specialist delegation warranted. Task complexity 8+ out of 10: agent teams.
Tight coupling or iterative review makes coordination essential. The failure mode for most users building on this stack is over-engineering. Running agent teams on tasks a single
agent would have handled fine is expensive and produces no better output. Start simple. Escalate only when the simpler architecture visibly fails. Part IX: MCP Servers MCP, Model
Context Protocol, connects Claude to external systems. Gmail. Calendar. Slack. CRM. Notion. Databases. APIs. Instead of copy-pasting data between tools, Claude reads and writes
directly. The consequence is that Claude moves from a reasoning system to a full operational participant in your business workflows. 9.1 What MCP does Each MCP server connects
Claude to one external tool. Once connected, Claude can call that tool's functions the same way it calls its internal tools. Gmail MCP: Claude drafts, sends, and replies to emails.
Calendar MCP: Claude checks availability, schedules meetings, and updates events. Linear or ClickUp MCP: Claude reads, creates, and updates tasks and projects. Notion MCP: Claude
reads and writes notes, meeting summaries, knowledge base entries. Perplexity MCP: Claude runs deep research via Perplexity's search API. Apify MCP: Claude scrapes LinkedIn,
Instagram, and other platforms using pre-built scrapers. Custom API MCP: Any service with an API can be connected via a custom MCP server. 9.2 The priority MCP connections for a
photographer MCP What Claude Can Do Why It Matters Gmail Draft, send, reply to emails. Search inbox. Triage. Half of a photographer's non-shoot time is email. Delegating it
recovers hours per week. Google Calendar Check availability. Schedule shoots. Block prep time. Send invites. Removes the back-and-forth of scheduling. Claude handles it directly.
Google Drive or cloud storage Read and write documents, images, contracts. Projects and book work live in Drive. Direct access eliminates upload friction. Notion or Obsidian Read
and write notes, SOPs, client files. The knowledge base becomes queryable. Claude pulls prior notes into current work. Perplexity Run deep research with live web data.
Higher-quality research than Claude's native web search for some query types. Apify Scrape LinkedIn, Instagram, Facebook for lead research. Lead enrichment for spec work pitches
and cold outreach. Stripe or payment processor View invoices, payments, and revenue data. Financial metrics available inside the workspace. The Revenue Stack numbers become
queryable. Canva or design tool Pull brand assets and design templates. Design tasks can be executed end-to-end inside the workspace. 9.3 Scoping MCPs per sub-agent A critical
technique. Each sub-agent should only see the MCPs it actually needs. A content-writer agent does not need CRM access. An operations agent does not need image generation tools.
Content-writer agent: File read/write only. No MCPs unless voice-specific. Research-specialist agent: Perplexity MCP, Apify MCP, web search. Operations agent: Gmail, Calendar,
Notion, CRM MCPs. Design-reviewer agent: File read, browser preview. No external MCPs. Scoping reduces the token overhead of MCP tool descriptions in each agent's context. It also
prevents agents from stepping on each other's domains. A content-writer with CRM access is a bug waiting to happen. 9.4 Token overhead management A practical concern that most
users hit eventually. Each MCP server's tool descriptions consume context window space. Connecting ten MCP servers can fill 10 to 20 percent of a context window with tool
definitions before any work begins. The newer Claude Code behavior: when MCP tool descriptions exceed 10 percent of the context window, Claude does not load all of them up front.
It uses an internal search tool to find the right MCP tool when needed. This means connecting many MCPs is less costly than it used to be. But the cost is not zero. Every tool
description still contributes some overhead. The working practice: connect the MCPs you actually use. Do not connect every MCP that sounds interesting. Remove unused MCPs
quarterly. When a workspace feels slow or outputs feel shallow, check the MCP count. An overstuffed MCP list degrades performance. 9.5 The security consideration An MCP server has
the permissions you grant it. A Gmail MCP can read every email in your inbox. A CRM MCP can modify every record. This is not a reason to avoid MCPs. It is a reason to review
permissions carefully and grant only the minimum access needed. Start with read-only MCP access wherever possible. Expand to write access only when the work requires it. Review
third-party MCP servers from unknown sources carefully. A malicious or badly-coded MCP can leak data. Separate sensitive work (finances, legal) into MCPs that only specific
sub-agents can access. Treat MCP configurations as secrets when they contain API keys or tokens. Do not commit them to public repositories. Part X: Claude Cowork and Dispatch

this series. Written here as a specific, reproducible process. The book-writing workflow is the most load-bearing single skill for a photographer building an authority business.
Direction Stack is the first product. The companion volumes are the second through fifth. Future books are the next decade of revenue. 12.1 Context discipline The single most
important concept for writing long-form work with Claude. Context windows fill up. Once they exceed about 95 percent capacity, Claude compresses and summarizes internally, losing
fine detail from earlier in the conversation. For book writing, this is catastrophic: the voice drifts, characters become inconsistent, plot details get dropped. Keep book-writing
context windows under 50,000 tokens. Always. Do not paste the entire prior manuscript into the chat. Condense each completed chapter into a 200 to 500 word summary that captures
the key details. Use Project Knowledge for the manuscript. Claude searches it selectively rather than loading it all. Start new chats for new chapters. Each chat handles one
chapter. The context stays focused. Keep the CLAUDE.md (or equivalent voice guide) updated and short. 200 to 500 words of voice rules beats 5,000 words of examples. 12.2 The book
workspace Every book should live in its own Project (or Claude Code workspace for heavier work). The structure: THE BOOK PROJECT STRUCTURE /manuscript - Current draft, chapter by
chapter /outline - Working outline. Updated as the book evolves. /voice - Voice rules. Hard prohibitions (no em dashes). Stylistic preferences. Reference passages from prior work
that exemplify the voice. /characters - Character sheets (for fiction) or persona profiles (for non-fiction) /research - Source material, interview notes, reference articles /swipe
- Examples of what good looks like. Passages from books you admire for specific reasons. /chapters - Chapter-by-chapter condensed summaries (for context in later chapters) 12.3 The
writing workflow Step 1. The outline Outline before writing. Always. Even for short books. The outline does not have to be final. It has to exist. Draft a chapter list with
one-line descriptions. For each chapter, write three to five bullet points of what the chapter covers. Use Claude to stress-test the outline. 'Here is the outline. What is missing?
What chapters could be combined? What single-line description is weakest?' Iterate until the outline feels complete. Lock it. Move to drafting. Step 2. The chapter drafting loop
Open a fresh chat for the chapter. Load the voice guide, the chapter outline, and the condensed summaries of prior chapters. Ask Claude to draft the chapter according to the
outline. Full pass. Do not interrupt. Read the draft. Note what works and what does not. Iterate within the conversation. 'Keep the structure but tighten section 2. The voice in
section 3 drifted toward consultant. Restore the field-operator tone.' When the chapter is 80 percent right, move to manual editing. Claude drafts. You finish. Once the chapter is
final, condense it to a 200 to 500 word summary. Save to /chapters. The summary (not the full chapter) gets loaded into the next chapter's context. Step 3. The voice audit Even
with a well-defined voice guide, drift happens. Every three to five chapters, run a voice audit. Load the voice guide plus the most recent three chapters. Ask Claude: 'Audit the
voice across these chapters. Identify every place the voice drifted from the guide. List specific sentences that need rewriting.' Review the list. Fix the drifts. Restore the voice
across the drafts. The earlier drift is caught, the cheaper it is to fix. A voice drift in chapter 3 that is caught in chapter 15 requires rewriting 12 chapters. 12.4 The marketing
assets Once the manuscript is complete, the marketing layer kicks in. Each asset has a specific Claude pattern. Asset Working Prompt Pattern Sales page copy Using the voice guide
plus the manuscript, write sales page copy for Gumroad. Lead with the transformation, not the feature list. Include a one-paragraph overview, three core promises, and four bullet
outcomes. Book blurb Write three book blurb variations: short (30 words), medium (80 words), long (150 words). Each one leads with the core tension the book resolves. Query letter
(for fiction or if pursuing traditional) Write three query letter variations with different hooks, different structures, different summaries. Then select the one most likely to get
a full request. Email newsletter launch Write a launch email to the existing list. Announce the book. Tell the story of why it was written. CTA to buy. Launch social posts Seven
platform-specific launch posts: LinkedIn, Instagram, TikTok, YouTube Shorts, Facebook, Substack, X. Each one native to the platform. The 100-post content series Generate 100
content hooks derived from the book. Each hook is standalone and can run as a social post. The library feeds months of content. 12.5 The Open Close pattern A specific technique for
getting better first drafts of marketing copy. Instead of asking for one version, ask for multiple, then ask Claude to choose. "Generate three query letter variations: - Variation
1: hook lead with the protagonist's betrayal - Variation 2: hook lead with the world-building - Variation 3: hook lead with the genre comparison For each, include the standard
query structure: hook, summary, bio, thanks. Then, acting as a literary agent, read all three and identify which one is most likely to result in a full manuscript request. Explain
why in two sentences." The pattern forces Claude to generate options and then self-evaluate. The output quality improves noticeably compared to asking for one version and hoping it
lands. 12.6 The AI-detection and publishing note For non-fiction books published on Amazon KDP or equivalent platforms: AI detection tools exist. Fully AI-generated content flags
at rates that can jeopardize an account. The working practice is AI-assisted, not AI-generated. Draft with Claude. Edit by hand. Run finished chapters through a rephrasing pass
(not the whole chapter, specific flagged paragraphs). Fact-check every claim before publishing. Claude can get facts wrong. Your reputation carries the error, not the tool's. Add
your voice. The chapters should read as you, not as Claude. If a chapter reads like the same tone as every AI-written book on Amazon, rewrite it. For direct-sale platforms
(Gumroad), AI-detection is less of a concern. But the quality standard is the same. The reader should not be able to tell which chapters Claude drafted and which were written from
scratch. Part XIII: The Operator Sequence How to actually build the Claude stack from zero. Day 1 through Year 2 and beyond. The sequence is compressible or expandable depending on
